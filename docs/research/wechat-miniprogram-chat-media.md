# 微信小程序聊天媒体选择与上传限制

研究对应：[#3 研究：确认微信小程序聊天媒体选择和上传限制](https://github.com/Witty-Felix/jiese-website/issues/3)

> **⚠️ 勘误（2026-09-30 修订 · 二次）**：本文档初版把「从聊天选文件」描述为**单级选择器**（直接弹出聊天文件列表），并断言不存在「先选聊天」这一级——**错误**。
>
> 第一次修订补上了「选择一个聊天」这一级，但仍**漏掉两个小程序自有页面**（进入时的空态落地页、选完后的已选暂存页）与一个**系统级「打开方式」面板**。第二次修订按第二段真机录屏补全为 **7 段完整链路**。
>
> **凡「官方文档未提及」都被写成「待观察」，不再写成「不存在」。** 本文档已被证伪两次，请以真机录屏为准绳。

## 结论

### 1. 真机观察到的完整链路（ima 客户端 · 导入微信文件 · 7 段）

两段录屏逐帧核对，**实际有 7 段**，其中第 2、4、7 段是前两版都漏掉的：

| # | 页面 | 宿主 | 关键元素 |
|---|---|---|---|
| 1 | 「+」**来源菜单** | ima 小程序 | 拍照 / 图片 / 录音 / 本地文件 / **微信文件** / 网页链接 / 笔记 / 个人知识库 / 新建文件夹 |
| 2 | **「使用以下方式打开」系统面板** | **系统 OS** | 微信 / 微信（分身）两个图标 + 「取消」。**这是跳出当前小程序、切到微信的动作** |
| 3 | 微信内**某个具体聊天**页 | 微信 | 落地时不先给列表，而是先停在**某个聊天**（录屏停在「贾瑞江」），左侧还能看到 ima 页面的残影 |
| 4 | ~~**「导入微信文件」空态页**~~ | 微信小程序 | ~~「暂无任何文件，点击开始上传」+ 按钮「⬆ 点击上传文件」~~ → **本页已决定省去（改一点即弹选择器），见实现约束第 3 条** |
| 5 | 「选择一个聊天」 | 微信原生选择器 | 搜索框 + 「最近转发」横向头像条 + 「最近聊天」列表（含「创建聊天」「分享至企业微信」） |
| 6 | 该聊天的**文件列表** | 微信原生选择器 | 「这个月」等按月分组；每行 发送者头像+昵称 / 文件名 / 类型徽标(WAV·MD) / 大小 / 相对日期 / **圆形单选**；顶部「取消」、右下「确定」；深色 OS 主题 |
| 7 | ~~**「导入微信文件」已选页**~~ | 微信小程序 | ~~「已选文件 1/20」+ 已选条目 + 底栏「继续添加 1/20」与「**确认导入**」~~ → **本页已决定省去，见实现约束第 3 条** |
| 8 | 「导入成功」toast → 回到知识库 | ima 小程序 | 文件落库并进入「解析中…%」 |

**要点**：
- 第 2 段是**系统级**「打开方式」面板（`Intent`/`OpenURL` 层），不是任何一方小程序的 UI——它证明**从 ima 跳到微信是一次跨 App 的显式跳转**，不是页面内导航。
- 第 4 与第 7 段是**微信侧小程序自己的页面**（白底、小程序胶囊按钮、左上角分享/返回图标），说明微信这边是「**小程序页面 → 原生选择器 → 回到小程序页面**」的三明治结构：小程序壳负责「空态引导」与「已选暂存 + 确认导入」，原生选择器只负责「选聊天 / 选文件」。
  **（这两页本项目都不做——见实现约束第 3 条。此处描述的是 ima 客户端的真机形态。）**
- 第 3 段说明**进入选择器前会先落到某个聊天**，而不是直接给聊天列表——这一步在用户视角里和后面的「选聊天」是「连在一起」的。
- 最大可导入数明确为 **20**（「已选文件 1/20」「继续添加 1/20」）。

### 2. 参与的 API：`wx.chooseMessageFile` 负责第 5–6 段

- **「从聊天选图片」**：`wx.chooseMessageFile({ type: 'image', count })`。
- **「聊天中作为文件发送的录音」**：`wx.chooseMessageFile({ type: 'file', extension: ['mp3','m4a','wav','aac'], count })`。官方把 `file` 定义为「除图片和视频之外的其它文件」，故聊天中以「文件」发送的音频属于目标范围。`extension` 过滤仅在 `type: 'file'` 时生效。
- **`count` 与真机一致**：真机显示 `1/20`，与官方 `count` 上限相符；我们业务上每个入口只取 1 份，所以传 `count: 1`。
- **选择结果可读取并上传**：`tempFiles[]` 每项含本地临时路径 `path`、字节大小 `size`、原始名称 `name`、分类 `type`。路径可交给 `wx.uploadFile` 的 `filePath`，也可由文件系统 API 读取。
- **必须及时处理临时文件**：临时文件只保证在当前小程序生命周期内有效，重启后不保证可用。选择后应立即校验并上传，**不能**把临时路径当长期 URL 或跨启动草稿凭证。

### 3. 链路归属：**已判定**（2026-09-30 联网取证）

这段链路横跨三层，必须分开看，否则会重复犯错。

**核心结论：第 4、7 段那两个白底页是 ima 自己写的小程序页面，不是微信官方模板。**
**原生选择器只负责第 5–6 段（选聊天 → 选文件 → 确定），选完即回调返回，不会自带任何「确认导入」页。**
（第 7 段在本项目中已被省去，见实现约束第 3 条；这里判定的对象是 **ima 客户端**的真实链路。）

| 段 | 归属（已判定） | 我们能否复用 |
|---|---|---|
| 1 来源菜单 | ima 自有 UI | ❌ 不复用（我们有自己的入口设计） |
| 2 「使用以下方式打开」 | **系统 OS** | ⚠️ 只在「从别的 App 唤起微信」时出现；我们的小程序**内部**发起不需要它 |
| 3 落到某个聊天 | 微信原生（选择器的一部分） | ✅ 间接复用 |
| 4 空态落地页「暂无任何文件 / 点击上传文件」 | ~~ima 自写的小程序页面~~ → **本项目已省去，不实现** | ⛔ **不做**（2026-10-01 拍板，见实现约束第 3 条） |
| 5–6 选聊天 / 选文件 / 确定 | **微信原生选择器**（`chooseMessageFile` 内部） | ✅ **一次调用即得** |
| 7 已选暂存「已选文件 1/20 / 继续添加 / 确认导入」 | ~~ima 自写的小程序页面~~ → **本项目已省去，不实现** | ⛔ **不做**（2026-10-01 拍板，见实现约束第 3 条） |
| 8 落库 toast + 解析进度 | ima 自有 | ❌ 不复用 |

> **落地口径**：上表是 **ima 客户端**的完整链路（用于判归属）。本项目实际实现 **4 段**，且
> **自建的小程序页面数为 0**：
> `我们的入口（点一下）→ 原生选择器：落到聊天 → 选聊天 → 选文件（确定即落子）`。
> 第 2 段不经过；第 4、7 段两页均不做（2026-10-01 拍板）。**整条取值链只是一次 `wx.chooseMessageFile()` 调用。**

#### 取证依据（4 条独立证据，指向同一结论）

1. **官方文档只描述「一个调用」**：[`wx.chooseMessageFile`](https://developers.weixin.qq.com/miniprogram/dev/api/media/image/wx.chooseMessageFile.html)
   的功能描述全文只有一句「**从客户端会话选择文件**」，参数是 `count` / `type` / `extension`，
   `success` 直接返回 `tempFiles[]`。**文档没有提到任何中间页面、任何「导入」页、任何「已选确认」步骤。**
2. **独立开发者复现的原生流程只有两页**（第三方博客，与 ima 无关）：
   「触发上传文件按钮点击事件，**就会调起微信的聊天界面**……然后，找到你聊天界面中的文件，**勾选好文件，点击确定**。
   选择文件上传的功能就完成了。」—— 选完「就完成了」，**没有第三个页面**。([来源](https://tech.qufami.com/read-11377.html))
3. **同一流程的另一次独立复现**，步骤写得更直白：
   「步骤2: 点击【附件上传】- 选择聊天记录里面的【文件传输助手】；
   步骤3: 选择xx作品后**关闭聊天记录弹框**后即可上传附件。」
   —— 「**关闭聊天记录弹框**」= 原生选择器本身就是一个**弹层**，关掉就回到自己的页面。([来源](https://www.cnblogs.com/LindaBlog/p/16492896.html))
4. **「选后确认」被明确描述为开发者自己要做的事**：
   「`wx.chooseMessageFile` 返回的 `tempFiles` 数组里……**你可以利用这些信息，在小程序里展示一个文件列表，让用户确认是否要上传**。
   这种『**先选后确认**』的流程……」 —— 说明第 7 段那种「已选列表 + 确认」**是应用侧自建的**，不是平台给的。
   ([来源](https://www.zhonweb.com/newsDetail.html?id=10993))

#### 这对我们意味着什么

- ✅ **好消息**：最复杂的一段（跨聊天聚合文件、按月分组、圆形单选、搜索、最近转发）**是官方的，一次 `wx.chooseMessageFile()` 调用就能拿到**。
  我们**不需要**自研聊天列表 / 文件列表，也**不需要**任何特权数据接口——这同时避开了隐私边界。
- ❌ **要自己做的**：真机第 4、7 段那两个「导入微信文件」页**是 ima 自建的**，不是官方白送。
  **但本项目两页都不做（2026-10-01 拍板）→ 自建的小程序页面数为 0**，整条取值链只是一次 API 调用。
- ⚠️ **注意区分**：ima 那两页之所以长得像微信小程序（白底 + 胶囊按钮），是因为**它们本来就是小程序页面**（ima 自己的），
  而不是因为官方提供了这个模板。**「长得像官方」≠「官方给的」**——这是本次最容易误判的地方。

> **不要重犯的错误**：不要因为「官方文档没写第 4、7 段」就断言它们不存在（它们确实存在，录屏为证）；
> 也不要因为「它们长得像微信小程序」就断言它们是官方模板（它们其实是 ima 自建的）。
> 正确做法是：**先分清「平台能力」与「应用自建 UI」两层**，再去查官方文档只承诺了哪一层。

### 4. 可直接依赖的结论（不受上述分歧影响）

- **网络前置条件**：`wx.request` / `wx.uploadFile` 只能访问小程序后台配置的服务器域名；须 HTTPS，不能用 IP 或 localhost，且按端口精确配置。上传域名必须纳入「服务器域名」。
- **平台读取上限与产品上限分开**：`FileSystemManager.readFile` 的单文件读取上限是 100 MB，`chooseMessageFile` 与 `wx.uploadFile` 不承诺统一的单文件选择/上传上限。经过 #26 的决策，本项目仍选择 100 MiB 作为小程序产品上限，因为当前链路依赖单次 `ArrayBuffer` + 单次 COS PUT；服务端与小程序共同执行该上限，并以 `tempFiles[].size` 预检。详见 ADR-0014。
- **微信语音消息不在能力范围内**：本票只覆盖会话中的图片，以及以普通文件发送的 MP3/M4A/WAV/AAC。`chooseMessageFile` 的官方类型是 `all`/`video`/`image`/`file`，**没有**读取微信语音消息的类型或接口，故继续明确排除微信语音。
- **普通 H5 不能调用该能力**：`wx.chooseMessageFile` 是小程序 API，不是 Web API。普通 H5 可用系统文件选择与拖拽拿到 `File`，但**没有**官方能力枚举或读取微信聊天文件列表。网页 JS-SDK 能力含 `chooseImage`/`uploadImage` 等，**不含** `chooseMessageFile`；H5 放进小程序 `web-view` 后可用 JSSDK 列表同样不含。需要聊天文件选择时**应提供独立小程序入口**（与 #5 的产品决策一致）。

## 本项目的 100 MiB 音频决策（2026-10-04）

小程序请求使用 `channel: "wechat-miniprogram"`，阅读录音严格允许 `size <= 104857600` 字节。选择回调超过边界时不得调用 `prepare`；服务端 `prepare` / `finalize` 也必须返回“微信小程序录音不得超过 100 MB”，并在产生提交标识、ima 临时媒体或登记副作用前拒绝。H5 省略通道标识，继续使用 200 MiB 契约。这里不引入 COS 分片、断点续传或字节级进度协议；结果未知仍复用原 `submission_id`。

详见 [ADR-0014](../adr/0014-wechat-miniprogram-audio-cap.md) 与 [实现票据 #27](https://github.com/Witty-Felix/jiese-website/issues/27)。

## 对本项目的实现约束

1. **本项目实际实现 4 段，且自建的小程序页面数为 0**：
   `我们的入口（点一下）→ 原生选择器：落到聊天 → 选聊天 → 选文件（确定即落子）`。
   真机的第 2 段不经过、第 4 与第 7 段两页均不做（见第 3 条）。**整条取值链只是一次 `chooseMessageFile()` 调用。**
2. **原型体现「点入口即弹原生选择器 → 确定即落子」**，不再有任何自建页面或中间态。
   - 选择前：材料槽处于「未选择」→ 点击入口，**直接拉起原生选择器**（对应真机第 4 段已省）。
   - 选择中：官方原生选择器（选聊天 → 选文件 → 确定 / 取消），**一次 API 调用**。
   - 选择后：**直接落子并回到打卡主流程**（对应真机第 7 段已省）。
   - 取消 / 退出 → 材料槽转「已取消」，**不是错误**（对应 `chooseMessageFile` 的 fail 回调）。
3. **真机第 4、7 段这两个 ima 自建页，本项目都不做（2026-10-01 用户拍板）**：
   - **第 ⑦ 段「已选暂存页」省去**：「确定」即最终确认，不再多一层「已选文件 1/20 + 继续添加 + 确认导入」。
   - **第 ④ 段「空态引导页」省去**：改为**一点即弹选择器**，点入口直接拉起原生选择器。
   - **取舍理由（第 ⑦ 段）**：本项目每个入口只取 1 份文件（第 4 条），「继续添加」在业务上无用；而「已选确认」这层与打卡表单里已有的「推进前勾选确认」重复，双层确认对成员是负担。
   - **取舍理由（第 ④ 段）**：该页在 ima 里承担的是「文件库空态 + 上传入口」，本项目没有文件库概念；而它承载的那句提示（「录音须由对方以『文件』发送——微信语音消息不能选」）在打卡表单的槽位说明里**已经存在**，不需要专门一页。
   - **工作量后果**：自建小程序页面 **2 → 1 → 0**。本项目在小程序侧只剩「调一次 API + 处理 `tempFiles`」，**这是本组决策的主要收益**。
   - **代价**：成员第一次点入口会直接从打卡页跳到全屏原生选择器，**少了一次「这是什么」的解释机会**。需在真机验证 (#6a) 后观察是否需要补文案，或把提示前移到槽位说明里。
4. **`count` 传 1**：真机上限是 20（`1/20`，那是 ima 自设的），业务上每个入口只要 1 份；我们不给「继续添加」也无需暴露 20。
5. 打卡表单分别提供「从聊天选图片」和「从聊天选录音文件」两个入口（**不再有独立的小程序页**）；录音入口用 `type: 'file'` 与四个扩展名过滤，并在客户端检查大小、扩展名与名称。
6. 服务端仍须重新检查扩展名、实际 MIME/文件头、大小以及登录/邀请码，**不信任**客户端传来的文件名、类型或大小。
7. 选择后直接进入上传流程，**避免**把 `wxfile://` 临时路径存入打卡草稿或跨启动传递。
8. `wx.uploadFile` 对配置域名发起 `multipart/form-data` HTTPS POST，**不能直接等同于** ADR-0005 浏览器对 COS 的预签名 PUT；后端复用、接口适配、是否新增小程序上传中转由 [#4](https://github.com/Witty-Felix/jiese-website/issues/4) 决定。
9. 普通 H5 保留系统文件选择与电脑端拖拽入口；**不要**在 H5 中承诺「浏览微信聊天并选择文件」。
10. **第 2 段（系统「打开方式」面板）不在我们可控范围**：它只在「从其他 App 唤起微信」时出现。我们的独立小程序内部调用 `chooseMessageFile` 时不会经过它，因此**原型不应画出这一段**，但要在文档里记明它的存在，以免再次误判链路起点。

## 待验证（真实设备 · 留证性质）

归属问题**已于 2026-09-30 联网取证判定**（见 §3），本票不再判定归属。剩下的只是**留证与回归**：

- **[#6a] 复核 `chooseMessageFile` 的完整链路**：在真机小程序（与我们自己的主体）中调用 `wx.chooseMessageFile({type:'file', count:1})`，确认：
  1. **直接弹出原生选择器**（选聊天 → 选文件），**不会**先出现「点击上传文件」空态页——因为那页是 ima 自建的；
  2. 「选择一个聊天」原生选择器如期出现，且第 5–6 段表现与 ima 录屏一致；
  3. **选完点「确定」后直接回调返回 `tempFiles`**，**不会**出现「已选文件 1/20 / 确认导入」页——那页同样是 ima 自建的。
  记录机型 / 微信版本 / 基础库版本。
- 若实测与上述预期不符（即确实出现了中间页），说明我们对 §3 的判定有误，需回来修订本文档并重新评估工作量。
