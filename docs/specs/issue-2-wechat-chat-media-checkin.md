# Spec：从微信聊天直接上传运动截图和阅读录音完成打卡

- 来源：GitHub Issue [#2：支持从微信聊天直接上传运动截图和阅读录音](https://github.com/Witty-Felix/jiese-website/issues/2)
- 类型：功能规格
- 规格日期：2026-10-04
- 更新日期：2026-10-06（Issue #32 用户认可自动上传边界，1.0.1 已发布）
- 目标：让成员不离开熟悉的微信素材来源即可完成一次完整打卡，同时保留 H5 的通用上传入口。

## Problem Statement

当前打卡入口要求成员先把运动截图和阅读录音变成系统文件，再通过网页普通文件选择器提交。对于主要在微信聊天中接收或发送材料的成员，这条路径会产生额外的保存、切换应用和重新查找成本；手机微信内的 H5 也不能直接读取聊天中的图片或“作为文件发送”的录音。

现有打卡的领域规则不能因为换入口而改变：一次打卡仍然由一条笔记、一张运动截图和一段阅读录音组成；昵称+邀请码仍是进入方式；内容仍需进入 ima 共享知识库「戒色」；打卡天数仍按自然日去重；同一天可以再次登记，但不能把网络重试误登记成新的打卡。

因此需要把“素材如何被选择”与“素材如何被登记”拆开：微信小程序和电脑端 H5 提供各自适合的取材入口，后端继续提供一套可验证、可重试、可区分通道限制的 `verify → prepare → COS PUT → finalize` 提交契约。

## Solution

提供两个独立但功能完整的打卡入口：

1. **微信小程序入口**
   - 在运动截图步骤直接调用微信原生 `chooseMessageFile` 的图片能力。
   - 在阅读录音步骤直接调用微信原生 `chooseMessageFile` 的普通文件能力，并按 `mp3`、`m4a`、`wav`、`aac` 扩展名过滤。
   - 每个步骤只取一份材料；原生选择器确认后立即接收结果，不建设“空态引导页”或“已选暂存页”。
   - 每份材料选择后立即校验类型和大小；两份材料齐备后自动申请凭证、读取临时文件并通过同一份 COS 预签名 PUT 契约上传；不得把 `wx.uploadFile` 当作现有预签名 PUT 的替代。
   - 上传完成后允许继续编辑感悟，点击“提交打卡”才冻结感悟并执行最终登记；结果未知重交复用冻结的提交。
   - 小程序请求显式携带 `channel: "wechat-miniprogram"`，录音有效上限为 100 MiB。

2. **电脑端 H5 入口**
   - 保留普通系统文件选择器作为通用入口。
   - 现有上传区域同时接受微信电脑版拖入的图片和“作为文件发送”的录音；实现以 `DataTransfer.files` 为准。
   - 拖拽不被浏览器或微信版本暴露为可用文件时，不能阻塞普通文件选择器；用户仍可点击区域选择本地文件。
   - H5 省略 `channel`，保持现有 200 MiB 录音契约。

两个入口都必须完成同一条业务链：昵称+邀请码校验、申请两份媒体预签名、客户端直接向 COS 并行 PUT、提交两份媒体回执和可选感悟、写入 ima 三项内容及 KV 统计。结果未知时，客户端只能重交同一次提交，不能重新申请媒体或重新上传。

## User Stories

1. 作为打卡成员，我希望在微信小程序中直接从聊天选择运动截图，以便不用先把图片保存到手机文件系统。
2. 作为打卡成员，我希望在微信小程序中直接选择聊天里“作为文件发送”的阅读录音，以便不用手动导出录音。
3. 作为打卡成员，我希望小程序的录音选择器只展示支持的音频扩展名，以便减少选错文件的机会。
4. 作为打卡成员，我希望图片和录音各有清晰的独立步骤，以便知道当前缺少哪一份必需材料。
5. 作为打卡成员，我希望取消原生选择器不会生成半成品提交，以便可以重新选择而不污染打卡记录。
6. 作为打卡成员，我希望小程序选择成功后立即看到材料已接收的状态，以便知道选择结果已经落到当前提交中。
7. 作为打卡成员，我希望小程序不再额外展示空态引导页，以便点击材料入口后直接进入微信原生选择器。
8. 作为打卡成员，我希望小程序不再要求先确认“已选材料”暂存页，以便原生选择器点击确定后就能继续处理。
9. 作为打卡成员，我希望小程序在两份材料齐备且临时文件仍然有效时自动读取和上传，以便不因重启小程序或拖延操作导致临时路径失效。
10. 作为打卡成员，我希望小程序在文件大小超过通道上限时立即得到明确提示，以便不等待一次必然失败的上传。
11. 作为打卡成员，我希望小程序在读取后的字节数与选择器报告的大小不一致时停止提交，以便避免登记不完整或损坏的材料。
12. 作为电脑端成员，我希望把微信电脑版中的聊天图片直接拖入运动截图区域，以便不用另存文件。
13. 作为电脑端成员，我希望把微信电脑版中“作为文件发送”的 M4A 或其他受支持录音直接拖入录音区域，以便保持现有工作习惯。
14. 作为电脑端成员，我希望仍能点击区域使用普通系统文件选择器，以便在拖拽不可用时有稳定的降级路径。
15. 作为电脑端成员，我希望拖入不受支持的文件时看到类型错误，而不是让页面进入无法恢复的上传状态。
16. 作为电脑端成员，我希望同一文件可以在清除后再次选择，以便修正误选的截图或录音。
17. 作为打卡成员，我希望两份必需材料都准备好后提交按钮才可用，以便不会产生缺少附件的打卡。
18. 作为打卡成员，我希望感悟仍然是可选的，并且与附件一起进入本次打卡笔记，以便可以只提交材料或补充文字。
19. 作为打卡成员，我希望看到上传和登记过程的进度或处理中状态，以便不会因为等待而重复点击提交。
20. 作为打卡成员，我希望服务端拒绝非法昵称、邀请码、文件类型和大小时收到稳定、可理解的错误信息，以便知道如何修正输入。
21. 作为打卡成员，我希望图片和录音的字节直接从客户端上传到 COS，以便避免经过 Pages Function 的大文件中转瓶颈。
22. 作为打卡成员，我希望 H5 与微信小程序都能复用同一套后端登记协议，以便不同入口最终产生相同的打卡结果。
23. 作为 H5 成员，我希望省略通道字段仍然得到原有的 200 MiB 录音上限，以便现有客户端不被新入口破坏。
24. 作为小程序成员，我希望通道标识被服务端严格识别，以便拼写错误不会静默落入 H5 的宽松契约。
25. 作为小程序成员，我希望 100 MiB 的录音边界值能够通过，而多 1 字节就被拒绝，以便客户端和服务端的限制一致。
26. 作为打卡成员，我希望 `prepare` 在任何媒体副作用前完成通道和大小校验，以便被拒绝的请求不会留下 ima 临时媒体或提交记录。
27. 作为打卡成员，我希望 `finalize` 在读取提交状态和写入 ima/KV 前再次完成同样的通道和大小校验，以便恶意或过期客户端不能绕过前置检查。
28. 作为打卡成员，我希望 `prepare` 签发一个代表本次提交的 `submission_id`，以便网络结果未知时可以安全重交。
29. 作为打卡成员，我希望结果未知时看到“重交本次登记”而不是被迫重新选择和上传材料，以便减少重复登记和重复流量。
30. 作为打卡成员，我希望重交沿用同一个 `submission_id`、两份媒体回执和通道标识，以便服务端能识别这是同一次提交。
31. 作为打卡成员，我希望已完成的提交再次到达服务端时返回 `already` 且不产生任何新的 ima 或 KV 副作用，以便安全应对重复点击和网络重试。
32. 作为打卡成员，我希望提交记录不存在、过期、昵称不匹配、日期不匹配或通道不匹配时收到冲突错误，以便错误回执不会被当成我的新打卡。
33. 作为打卡成员，我希望同一天已有打卡时先看到确认，再决定是否再次登记，以便“安全重试”和“我确实要再打一次”不会混为一谈。
34. 作为打卡成员，我希望确认再次登记后仍然可以产生第二次内容记录，但打卡天数不会重复增加，以便保留“同一天可多次打卡”的产品规则。
35. 作为打卡成员，我希望三项内容使用同一个日期文件夹和用户文件夹归档，以便截图、录音和笔记始终属于同一次打卡。
36. 作为打卡成员，我希望 ima 目录创建失败时打卡仍按既定降级规则继续，并在响应中暴露实际目录级别，以便目录故障不会被伪装成完全成功。
37. 作为打卡成员，我希望统计写入失败不会把已进入 ima 的打卡误报为失败，以便可以通过后续重试补齐统计而不重复写入内容。
38. 作为打卡成员，我希望提交成功页面和打卡榜能区分新登记与已登记结果，以便知道这次操作是否真的新增了内容。
39. 作为管理员，我希望通道限制、幂等状态和统计状态在日志或响应中可诊断，以便定位上传失败、结果未知和最终一致延迟问题。
40. 作为发布负责人，我希望小程序调用的 API 主机和实际 COS HTTPS 主机可以加入微信服务器域名配置，以便真机验收和发布审核不依赖临时地址。
41. 作为发布负责人，我希望 API 稳定主机使用 `api.324614917.xyz`，并允许后续从 Cloudflare Pages 迁移到自有服务器而不改变小程序配置，以便降低迁移成本。
42. 作为成员，我希望 H5 与小程序各自保持完整打卡入口，但不共享跨端草稿或上传状态，以便一个设备的半成品不会意外污染另一个设备。

## Implementation Decisions

### 1. 最高层 seam：一次完整提交契约

以“提交一次完整打卡”作为主要实现和验收 seam，而不是分别为每个界面重写一套上传后端。客户端差异只存在于材料选择和本地读取；从 `verify` 开始，两端共享 `prepare → COS PUT ×2 → finalize` 的登记契约。

### 2. 入口关系与选择行为

- H5 和微信小程序是两个独立、完整的打卡入口，共享昵称+邀请码和后端登记协议。
- 小程序采用分步材料向导：运动截图和阅读录音各有一个直接调用原生选择器的入口。
- 小程序不建设自有的空态引导页或已选暂存页；原生选择器确认即落子。
- 小程序图片选择使用微信聊天图片能力；录音选择使用微信聊天普通文件能力，并限制扩展名为 `mp3`、`m4a`、`wav`、`aac`；每个入口只接收一份文件。
- 临时文件只在当前小程序生命周期内视为可用。每份选择成功后立即执行类型和大小校验；两份齐备后自动读取、校验字节长度并上传，不把临时路径当作长期草稿凭证。
- H5 使用现有文件区域，同时支持普通系统选择器和拖放。拖放逻辑以 `DataTransfer.files` 为输入；`DataTransfer.items` 或微信私有数据不作为成功依据。
- 当拖放未提供可用文件时，页面必须保留并提示普通文件选择路径，不要求识别所有微信版本或浏览器私有行为。

### 3. 文件类型和大小契约

- 运动截图只接受 PNG、JPEG/JPG、WebP，硬上限为 30 MiB（31,457,280 字节）。
- H5 音频接受 MP3、M4A、WAV、AAC，通道字段省略时硬上限为 200 MiB（209,715,200 字节）。
- 微信小程序音频接受同样的四类格式，但必须携带精确的 `channel: "wechat-miniprogram"`，硬上限为 100 MiB（104,857,600 字节），边界值允许，超过 1 字节即拒绝。
- `channel` 省略表示兼容既有 H5 契约；任何已提供但不受支持的通道值都返回请求错误，不能静默当作 H5。
- 产品提示可以写“100 MB”，但协议判断、测试和服务端边界使用精确的 MiB 字节数。
- 限制必须在客户端预检、`prepare` 和 `finalize` 三处保持一致；拒绝应发生在产生 `submission_id`、调用 `create_media`、读取提交状态或执行 ima/KV 登记副作用之前。

### 4. 后端 API 契约

- `verify` 负责校验昵称+邀请码，并按现有目录规则确保用户文件夹；目录失败不得阻断登录，但必须暴露降级事实。
- `prepare` 接收昵称、邀请码、图片元数据、录音元数据和可选通道标识；成功时签发 `submission_id`，为两份媒体分别返回 `media_id`、COS 对象键、COS URL、临时授权和临时 token。
- 客户端使用返回凭证分别向 COS 发起单次 PUT；两份材料可以并行上传。服务端不接收大文件字节，也不使用 `wx.uploadFile` 替代预签名 PUT。
- `finalize` 接收昵称、邀请码、`submission_id`、通道标识、两份 COS 回执、可选感悟和重复日期确认标记；服务端校验回执格式、媒体类型、对象键、大小、提交身份和当前日期后，才写入 ima 与统计。
- 成功的新登记返回 `status: "new"`；同一提交的安全重交返回 `status: "already"`，并保证不重复写入 ima。统计占位未完成时，`already` 路径可以只补写统计，不得重新登记媒体或笔记。
- 日期以 Asia/Shanghai 为准；打卡笔记、用户文件夹、日期文件夹、统计键和幂等记录必须使用同一日期口径。
- API 稳定主机采用 `api.324614917.xyz`；H5 站点可继续使用现有地址；COS 保持独立 HTTPS 直传主机。

### 5. 提交幂等与重复日期

- `prepare` 生成服务端随机 `submission_id`，并以 `submission:<uuid>` 保存昵称、日期、状态、时间戳和小程序通道信息（如有），保留 24 小时。
- 提交状态至少区分 `prepared`、`inflight` 和 `done`。同一提交在短时间并发重交时应被软锁保护；软锁过期后应可恢复，不得永久阻塞成员。
- `finalize` 必须在任何写入前处理未知、过期、身份不匹配、日期不匹配和通道不匹配的提交。
- `done` 提交再次 finalize 时返回 `already`，不再次调用 ima、不重复写统计；若此前统计只写入占位，则只补齐统计状态。
- 本日重复判断使用单键读取作为提前提示和权威闸门；普通重复必须经过用户显式确认，确认后带 `allow_duplicate_day` 放行。
- “同一天可多次打卡”保持不变；幂等只约束同一个 `submission_id` 的重试，不把昵称+日期作为天然幂等键。
- ima 落库成功后要先把提交状态钉为 `done`，再写统计；这样统计失败可以补救，而已写入 ima 的内容不会因结果未知被再次登记。

### 6. 目录、内容和统计

- 一次打卡仍生成一条笔记、一张运动截图和一段阅读录音。
- 三项内容优先落在“用户文件夹 → 日期文件夹”；目录能力不可用时沿用现有分层降级，打卡不因目录失败而失败。
- 统计仍按用户和自然日去重；重复登记保留内容留痕，但不重复增加打卡天数。
- 删除边界不变：站内管理功能只处理既有 KV 统计记录，ima 内容不提供站内删除通道。

### 7. 明确不采用的技术方案

- 不把 `wx.uploadFile` 当成现有预签名 COS PUT 的替代协议。
- 不为本规格引入 COS 分片、断点续传、凭证续期、可恢复上传或字节级进度协议。
- 不通过昵称+日期做天然幂等，因为这会破坏同一天多次打卡。
- 不跨端共享草稿、提交检查点或上传状态；每个入口只管理自己的当前提交。

## Testing Decisions

### 测试原则

测试外部可观察行为和协议边界，不锁定 DOM 结构、函数私有实现或具体供应商 SDK 调用顺序。优先从完整提交 seam 验证“用户是否能完成一次正确打卡、失败是否无副作用、重试是否安全”。

### 必须覆盖的测试面

1. **小程序选择与前置校验**
   - 图片和录音分别成功调用对应原生选择能力。
   - 取消选择不会调用 `prepare`。
   - 支持的扩展名通过，不支持的扩展名被拒绝。
   - 100 MiB 音频通过；100 MiB+1 字节在选择回调中被拒绝，且不调用 `prepare`。
   - `readFile` 返回字节数与选择器元数据不一致时停止，且不调用 COS PUT。
   - 两份材料齐备后自动读取当前生命周期的临时路径，不作为跨启动草稿保存。
   - 上传阶段不调用 finalize；上传后编辑感悟并显式提交时才登记。结果未知后不允许改变冻结的感悟或重新上传。

2. **H5 文件入口和降级**
   - 普通系统文件选择器仍可完成图片和录音选择。
   - Chrome 基线中微信电脑版拖入图片和 M4A 能从真实 `DataTransfer.files` 进入表单。
   - 不同浏览器或微信版本没有可用 `DataTransfer.files` 时，普通文件选择器仍可用并给出降级提示。
   - 清除附件后可以再次选择同一个文件；类型和大小错误不会留下旧的已选状态。

3. **共享 API 契约**
   - H5 省略通道时，200 MiB 音频边界通过，超过 1 字节失败。
   - 小程序通道必须回传同一精确标识；未知或拼写错误通道失败。
   - `prepare` 的超限拒绝发生在 `submission_id` 和 `create_media` 之前，且不产生 KV 或 ima 副作用。
   - `finalize` 的超限拒绝发生在读取提交状态和任何登记副作用之前。
   - 邀请码、昵称、媒体类型、媒体回执、对象键和感悟长度的既有校验继续有效。

4. **幂等和结果未知**
   - 同一 `submission_id` 的第二次 finalize 返回 `already`，不再次触碰 ima；统计占位只允许补写统计。
   - 未签发、过期、昵称不匹配、日期不匹配和通道不匹配的提交返回冲突，且不登记。
   - `inflight` 软锁能阻止短时间并发重交，过期后能够恢复。
   - 结果未知后的客户端重交不再调用 `prepare`，不再上传 COS，复用原提交检查点和媒体回执。
   - 本日已有打卡时先返回重复提示；未确认不写入，确认后按同一天多次打卡规则放行。

5. **ima、目录和统计**
   - 正常流程产生三项内容，并使用同一用户/日期目录上下文。
   - 用户文件夹或日期文件夹创建失败时遵守既有降级规则，并在响应中准确报告目录级别。
   - ima 成功而统计失败时返回 `stats_updated: false`；后续安全重交可以补齐统计且不重复写 ima。
   - 已删除日期标记在合法重新打卡后按既有规则撤销。

### 测试 prior art

沿用仓库已经形成的三类 prior art：端点级集成测试（用 KV 与 ima 出站桩验证契约）、浏览器/DOM 流程测试（驱动真实页面验证状态迁移）、以及真实设备冒烟矩阵（验证微信原生选择器、临时文件和 COS PUT）。新增通道限制时，客户端选择策略、服务端双闸门、幂等回执和 H5 兼容性应作为同一回归矩阵维护。

真机基线记录为 MAA-AN00、Android 16、微信 8.0.78、基础库 3.17.3；该基线证明小文件的 `chooseMessageFile → verify → prepare → readFile → COS PUT ×2 → finalize` 链路可用，但不等于已经完成 100 MiB 真实录音压力测试。

## Out of Scope

- 读取、转换或上传微信语音消息；只支持聊天图片和聊天中“作为文件发送”的受支持录音。
- 网页直接读取微信聊天记录，或在网页中嵌入、搜索微信聊天文件列表。
- 让 H5 直接获得微信聊天选择能力；H5 只提供普通文件选择和桌面拖放。
- 多文件批量打卡、视频上传、录音转码、音频内容识别或自动审核。
- COS 分片上传、断点续传、凭证续期、可恢复上传和字节级上传进度。
- 跨端共享草稿、共享临时路径、共享提交状态或让小程序依赖 H5 页面。
- 以昵称+日期替代 `submission_id` 的全局幂等设计。
- 站内删除 ima 知识库内容。

## Further Notes

- 本规格把 Issue #2 map 中已经拍板的选择统一为可实现的行为契约；它不是“已部署完成”的证明。真机开发工具前置已具备，但服务器域名白名单、实际 COS HTTPS 主机和发布审核条件仍需在部署环境逐项验收。
- Issue #2 当前仍保留一项兼容性风险：电脑端微信拖拽在不同微信版本和浏览器中的行为尚未全部验证。本规格的安全默认值是：只接受真实 `DataTransfer.files`，无法获得文件时保留普通文件选择，不把兼容性猜测当成成功。
- 2026-10-03 的真机基线已经验证小程序从原生选择到 COS PUT 再到 finalize 的完整成功路径；本规格不把该基线外推为所有设备、所有微信版本或 100 MiB 音频压力测试结论。
- H5 与小程序的产品关系保持独立完整入口；H5 的 200 MiB 契约不能为了小程序的 100 MiB 限制而收紧。
- 结果未知的主动作是“重交本次登记”；`already` 表示此前已登记、本次未新增，`new` 表示本次产生了新登记；打卡榜核对只能作为辅助信息，不能替代幂等契约。
- 发布前的最低验收门槛是：两端的类型/大小边界一致；拒绝路径无副作用；同一提交可安全重交；H5 旧契约保持兼容；Chrome 拖拽基线和普通选择器降级路径均通过。
