# ADR 0002 — 登录采用昵称 + 邀请码，不建用户表

日期：2026-09-25
状态：已接受

## 背景

需要多用户使用，但现有架构无数据库。三种候选：昵称+邀请码、每人专属打卡码、用户名+密码（需 D1/KV 用户表）。

## 决策

采用**昵称 + 共享邀请码**：

- 前端登录页输入昵称与邀请码；邀请码校验放在 Function 端（`POST /api/verify`，邀请码存 Pages Secret，不进前端代码）。
- **昵称即身份**：打卡落库的文件夹名、笔记标题、统计榜均以昵称区分。
- 昵称做格式约束（2–16 字符，去首尾空格），不设密码、不存会话；打卡请求需携带邀请码或校验后签发的轻量票据，Function 端复核。

## 理由

- 零数据库、零密码管理，代码量与攻击面最小，符合 Graph Engineering 的「最简单、可靠、经济」原则。
- 本站是熟人小圈子使用场景，邀请码足以控制准入。

## 后果

- 同名昵称会被视为同一用户（可在邀请阶段约定昵称唯一）。
- 无密码意味着知道邀请码+随便起个昵称即可打卡——可接受；若未来需要防冒用，再升级为专属打卡码（ADR 记录升级路径即可）。
