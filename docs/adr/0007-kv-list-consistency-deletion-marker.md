# ADR 0007 — 用删除标记绕开 KV list 的最终一致延迟

日期：2026-09-25
状态：已接受
关联：ADR-0004（KV 统计）、ADR-0006（管理员删除）

## 背景

删除功能上线后出现两个真实故障：

1. 管理员删除后，榜单十几秒后才消失（ADR-0006 已缓解）。
2. **整户清空后立即刷新，记录「复活」**；连点五六次刷新，等 KV 同步窗口过去才真正消失。

根因是 Cloudflare KV 的一致性模型：

- `delete` / `put` 对**单个键**是即时的——删除本身当即成功（ADR-0006 的审计记录可证）。
- 但 `list()` 的结果存在**最长约 60 秒的最终一致延迟**：键已删，list 仍会返回该键名。

而 `/api/stats` 正是靠 `list({ prefix: 'checkin:' })` 枚举键来算榜单的。于是「删除成功」与「榜单可见」之间被 list 的同步窗口隔开。ADR-0006 的乐观更新只解决了**页面不重新加载**的路径；用户按 F5 会重新走 `/api/stats`，读到旧列表 → 记录复活。

## 决策

引入**删除标记（Deletion Marker）**，把删除事实写在一个**单键**上，让读取走 `get` 而不是 `list`：

1. 删除标记键：`deleted:<昵称>`，值为 `{ dates: ["yyyy-mm-dd", ...], ts }` —— 该用户被删掉的日期集合。
2. 删除时（`DELETE /api/admin/checkin`）把本次删除的日期并入标记。
3. `/api/stats` 用 `list` 拿到名单后，对名单内每个用户**各做一次 `get` 读标记**，把已删日期从日期集合里减掉；减空即该用户不出现在榜单。
4. 重新打卡（`finalize`）时**先撤销该日期的标记、再写打卡记录**，保证「删了当天重打」不会被标记误隐藏。

之所以有效：KV 在写入发生的 colo 会同步失效该键的读缓存，因此**紧接着同一客户端发起的统计请求可以读到最新标记**；而 list 结果没有这条保证。用户在浏览器里「清空 → 立刻刷新」的请求路径恰好满足这一条件（同 IP → 同 colo）。

## 理由

- **只加一层薄薄的辅助数据**：不迁移数据、不引入新组件、不改打卡主流程；`checkin:*` 仍是唯一事实来源，标记只是「这段时间内请忽略这些键」的提示。
- **失败模式（降级方向统一选「多显示」而非「隐藏真实记录」）**：
  - 统计侧读到标记失败 → 视为无标记，最多短暂多显示已删行；
  - 写标记失败 → 不回滚删除，同样只是多显示；
  - **撤销标记时读失败 → 覆写为空标记**（`removeDeletedDate`）。这是唯一会「隐藏」的方向，因此宁可清掉整块标记（最多让更早的已删行短暂复现），也不留下能永久隐藏这条合法打卡的残留标记；
  - 标记整体丢失的代价有界：list 收敛后已删键自然消失，标记只是那几十秒窗口内的提示，属可再生辅助数据。
- **`finalize` 中「写打卡记录」与「撤销标记」必须分两次 try**：标记操作失败不能连带让这条合法打卡写不进去（记录丢失不可逆，标记残留可自愈）。
- **重新打卡自动撤销标记**，避免「管理员删错一天 → 用户当天重打 → 打卡被隐藏」这类次生事故。
- 相比逐键 `get` 校验（list 拿到 N 个键就发 N 个子请求），本方案每个用户至多 1 次 `get`，且只在存在标记时产生，**受 Workers 子请求上限约束更安全**——本站按 20 人 × 60 天估算就是 1200 个键，逐键 get 会直接撞上子请求限制。

## 后果

- `/api/stats` 增加「每个上榜用户 1 次 `get`」的开销（KV 读取廉价，可忽略）。
- `deleted:` 键会随删除操作累积；单键存日期数组并有上限（500 条，超出裁掉最旧），长期不会膨胀到影响读性能。
- 标记遵循与 list 相同的最终一致边界：**跨设备/跨 colo 的观察者**仍可能看到最多约 60 秒的残留。这是平台特性，无法在 KV 层彻底消除。
- 删除标记与审计记录一样，只服务于统计读取，不展示给普通成员；`/api/stats` 只 list `checkin:` 前缀，标记不占榜单。
- **配套：静态资源缓存击穿**。目标是「修复已上线但用户仍跑旧前端」——这类「陈旧读取」与 KV list 延迟同源，都是读到旧副本。两道措施：
  1. `_headers` 对 `/app.js`、`/styles.css` 下发 `Cache-Control: no-cache`：**持久保证**，每次使用前带 ETag 回源校验（未变走 304，开销极小，变了立刻拿到新版本）。这是主要机制。
  2. `index.html` 里的 `?v=<版本>`：**一次性**冲掉规则生效前已存在于浏览器里的旧副本。有了 `_headers`，后续改动不再必须递增版本号，因此不存在「两处版本号手工同步」的漂移风险。
- **升级路径**：若日后要求强一致（例如成员数上升、或跨地域成员抱怨延迟），应把打卡统计迁到 **Cloudflare D1**（关系型、强一致），键模型改为 `checkin(nickname, date)` 唯一索引，删除即真实删除、无需标记。本期不改，因为收益不及迁移成本与回归风险。

## 验证记录

| 验证 | 方式 | 结果 |
|------|------|------|
| 逻辑正确性（含 60s 陈旧 list 的最坏情况） | 桩化内存 KV 精确模拟「list 缓存定格不刷新」，直接调用真实 handler：`stats.js` / `admin/checkin.js` / `_stats.js` | 17/17 通过。关键用例：list 完全陈旧时，清空后立刻拉统计仍不含该用户；删当天后重打不被误隐藏；标记不可读时撤销降级为空标记 |
| 前端表单重置（Bug A） | jsdom 加载真实 `index.html` + `app.js`，跑完整「选文件 → 填感悟 → 提交」流程（fetch/XHR 桩化） | 15/15 通过。含提交后预览清空、`file input` 清空、按钮回锁、草稿清除，及「重置后可再次选文件」的反向验证 |
| 生产端用户场景 | 种子两键 → 清空 → **同一脚本内毫秒间隔**立即拉 `/api/stats` | 该行立即消失，未复现「复活」 |
| 标记是否承重（对照实验） | 清空后删除 `deleted:` 标记（约 20s 后），若无 list 延迟则该行不应复活 | **未复活** → 该环境此 PoP 的 list 已收敛，本次观测无法证明标记是决定性因素 |
| 真实数据 | 复盘 `audit:del:` 审计链 + `checkin:` 前缀清点 | 见下 |

**诚实结论**：本次未能从当前网络环境复现出长时间（>20s）的 list 陈旧窗口，因此**删除标记属于「针对已记录最坏情况的保险」，而非本次故障的唯一或已证实的成因**。用户此前观察到的「刷新五六次才消失」更可能由两层叠加造成：① 服务端 list 的最终一致（KV 文档确认最长约 60s，本环境未复现不代表不存在）；② 浏览器/中间层缓存了 `/api/stats` 响应——该层已在上一版用 `Cache-Control: no-store` + fetch `{cache:'no-store'}` 修复，但在其生效前浏览器已缓存的副本会持续到自身新鲜期结束，这恰好解释了「连点多次才消失」。两层现在都有对应防线。

**复盘结论（审计链证据）**：榜单为空是用户本人在 15:02 / 15:04 / 15:06（北京时间）连续三次执行「整户清空 / 单条删除」的结果，三次操作均记录在案（`deleted:1` ×3），删除对象均为自己的打卡记录，属预期行为；同期提交的打卡记录即被这几次清空删除。测试数据与测试审计键已清理，未触碰任何真实记录。

## 备选方案（未采纳）

| 方案 | 否决原因 |
|------|----------|
| 逐键 `get` 校验存在性 | 子请求数随键数线性增长，会撞上 Workers 子请求上限 |
| 客户端持久化「本地已删」过滤 | 引入第二个事实来源，跨设备不一致，且会与重新打卡冲突 |
| 改用 D1 / Durable Objects | 需迁移数据与改写三个端点，回归面大；本期问题不足以支撑 |
| 继续依赖乐观更新 | 已被证伪：F5 后仍走 `/api/stats`，回到同一条陈旧 list 路径 |

## 代码审查处置（双轴审查，固定点 `ec9e35f`）

审查发现的问题与处置，全部已修复并纳入回归用例：

| # | 轴 | 问题 | 处置 |
|---|----|------|------|
| 1 | Spec | `finalize` 把「撤销标记」与「写打卡记录」放进同一个 `try`：标记操作抛错会导致合法打卡记录根本不写入（记录丢失不可逆） | 拆成两次独立 `try`：先写记录，再撤销标记；任一失败都计入 `statsUpdated=false` |
| 2 | Spec | 标记读失败时 `removeDeletedDate` 静默返回，残留标记会**永久隐藏**该日合法重打记录，与本文档的失败模式声明矛盾 | 改为「读失败 → 覆写空标记」，降级方向明确选「多显示」；失败模式章节按实际行为重写 |
| 3 | Spec | `clearUser` 写死 `applyRowUpdate(nickname, null)`，忽略响应 `row`；与 `deleteDay` 不一致，竞态下乐观 UI 会与刷新后的榜单打架 | 与 `deleteDay` 统一：优先用 `row`，缺字段才回源重拉 |
| 4 | Spec | 空键集清空仍写入 `{dates:[]}` 垃圾标记键 | `addDeletedDates` 在无新增日期时直接返回 |
| 5 | Standards | `reset()` 与「移除」按钮回调重复实现同一套清理，且后者漏清 `picked.innerHTML` | 回调直接调用 `reset()`，单一实现 |
| 6 | Standards | `deleted:` 键拼接、标记写入形状、`checkin:` 键名解析三处重复，口径易漂移 | 抽出 `deletedKey()` / `writeDeletedDates()` / `parseCheckinKey()`，`stats.js` 与 `admin/checkin.js` 共用 |
| 7 | Standards | 「扣除标记 → 算行或 null」在 `stats.js` 与 `admin/checkin.js` 各写一份 | 抽出 `computeRowExcluding()`，统计与删除响应同口径由代码保证 |
| 8 | Standards | `rowFromKeys(..., deleted)` 的参数名与同文件计数变量 `deleted` 同名不同义 | 参数改为 `deletedDates` / 直接由共享函数承担 |
| 9 | Standards | 响应新增 `marked` 字段前端从不消费（未使用钩子） | 前端 `markWarn()` 消费：标记写入失败时在提示里告知「刷新后可能短暂复现」，把钩子变成真实防呆 |
| 10 | Spec | `?v=` 版本号硬编码两处、需手工同步，属易漂移范围外改动 | 新增 `_headers` 下发 `Cache-Control: no-cache` 作为持久保证；`?v=` 降级为一次性冲缓存手段，不再需要同步维护 |
