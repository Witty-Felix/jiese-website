# ADR 0010 — finalize 幂等键：`submission_id` 与自然日确认闸门

日期：2026-10-01
状态：已接受

## 背景

`prepare → 浏览器直传 COS → finalize` 三段式（ADR-0005）里，**第三段的结果是不可靠的**：
上传已经成功、素材已经躺在 COS 上，但 finalize 的响应可能丢在半路（网络中断、网关超时、页面被杀）。
此刻用户面对的是一个无法回答的问题——**「我到底打卡成功了没有？」**

配套的小程序原型（#6）对这条路径的取舍是「只引导核对、不给重交按钮」，因为当时后端**做不到安全重交**：
服务端没有幂等键，重交会把一次已成功的登记写成两次，而 **ima 知识库侧没有任何站内删除通道**
（这是本项目的硬约束），多写进去的素材永远收不回来。

那道「去打卡榜核对」的人工兜底**本身也不可靠**：`/api/stats` 靠 KV `list()` 枚举 `checkin:*` 算出来，
而 `list()` 有最长约 60 秒的最终一致延迟（README「已知限制」第 1 条）。最需要它准的那几十秒，
它不保证准——用户看到「今天没记录」，从头重来一次，反而制造了真正的重复登记。

用户已于 2026-09-30 拍板：**要加幂等键**。

## 决策

分三层，各管一件事。

### 1. 提交身份：`prepare` 签发 `submission_id`，`finalize` 按它去重

- `POST /api/prepare` 在 `create_media` **之前**生成 `crypto.randomUUID()` 并落一条 KV 记录
  `submission:<id>` = `{nickname, date, state, ts}`（TTL 24 小时），随响应下发 `submission_id`。
- `POST /api/finalize` 要求回传这个 `submission_id`，在**任何写入之前**判完：
  - 记录不存在 / 已过期 → `409 submission_unknown`，**不落库**；
  - 昵称或日期与记录不符 → `409 submission_mismatch`，**不落库**；
  - `state === done` → 返回 `{ok:true, status:"already"}`，**一个字都不写**；
  - `state === inflight` 且时间戳在 60 秒内 → `409 inflight`（软锁）。
- 状态机 `prepared → inflight → done`，键名与口径集中在 `functions/api/_submission.js`。

**关键前提：客户端的重交必须复用同一次 `prepare` 的回执**（`submission_id` + 两个 `media_id`/`cos_key`）。
重新 `prepare` 会换一个新的 id，服务端就认不出是同一次提交了——那样 (a) 等于白做。
因此前端加了一份 `localStorage` **提交检查点**（按昵称分键，跨天作废），失败后主按钮变成
「重交本次登记」，跳过 prepare 与直传、只重发 finalize。

### 2. 自然日闸门：只确认、不拒绝

- `prepare` 与 `finalize` 都先用**单键 `get checkin:<日期>:<昵称>`** 判本日是否已有记录
  （单键读是即时的，不像 `list()` 有延迟）。`prepare` 的那次是**提前量**——在上传 200MB 之前就问；
  `finalize` 的那次是**权威**——它才是决定写不写的地方。
- 已有记录且客户端未带 `allow_duplicate_day: true` → `409 duplicate_day`，提示「你今天已经打过卡了，
  确认要再登记一次吗？」，前端**就地**弹确认（不用 `window.confirm`：它是在 `await` 之后才弹的，
  已脱离用户手势上下文，微信内置浏览器会直接拦掉）；用户确认后才带标记重发。
- **「同一天可多次打卡」这条产品规则原样保留**。本票没有授权改产品规则，`(b) 按昵称+日期天然幂等`
  之所以不选，就是因为它必须放弃这条规则、要回到地图层面另行确认。这里做的是把重复登记
  **从静默发生改成用户显式选择**——顺带就落成了票里第 5 条问的「再打一次入口」。

### 3. 分界线：素材进 ima 之后，先把「已登记」钉死

三样内容写入 ima 成功的那一刻，**立刻**写 `state: done`（带 `stats_updated: false` 占位），
再去写 KV 统计，最后把占位覆盖成真值。

顺序是刻意的：ima 侧没有删除通道，素材重复写进去就永远回不来；反过来，统计晚一步是有救的——
`already` 路径发现 `stats_updated !== true` 时会**补写一次**统计（`checkin` 是覆盖写、
撤销删除标记是定点删，两次写都幂等，不会多算一天）。正常情况 `already` 零副作用。

## 理由

- **为什么由 `prepare` 签发，而不是复用 `image.media_id` 当键**：`finalize` 的入参全是客户端可伪造的
  （ADR-0005 自己注明「只做格式校验，不回查 COS」，持邀请码者本就可任意打卡，威胁等级不变）。
  由服务端签发并绑定 `{昵称, 日期}`，重交时顺手挡住「拿别人的回执来登记」。显式字段也把幂等键
  与 ima 的 `media_id` 命名解耦，代价只是两端多传一个字符串。
- **与 ADR-0005 记下的升级路径同源**：该 ADR 已经写着「如需加固，prepare 改发 HMAC 票据即可」。
  `submission_id` 就是那条路的第一段——将来要加防伪只需给它签名，不必再动契约形状。
- **不选 (b)「昵称 + 日期天然幂等」**：它会与「同一天可多次打卡」正面冲突，且把
  「重试」与「用户真想再打一次」压成同一件事——前者要求静默吸收，后者要求显式放行，
  压成一个就必然错一个。
- **自然日闸门放两处**：只放 `finalize` 会让成员传完 200MB 才被挡；只放 `prepare` 则客户端可以不问，
  不够权威。两处都只是对单个键做一次 `get`，成本可以忽略。

## 后果

- `prepare` 响应新增 `submission_id`、`already_today`；`finalize` 请求新增 `submission_id`、
  可选 `allow_duplicate_day`，响应新增 `status: "new" | "already"`，并新增 `409` 一类状态冲突码。
  H5 已同步；小程序尚未开发，其上传链路的「结果未知」分支按本 ADR 实现，不再需要「禁止重交」的妥协。
- KV 新增键空间 `submission:<uuid>`（TTL 24h）。每次打卡多 2～3 次 KV 写（落记录、置 inflight、
  钉 done、覆盖真值），对本站规模可以忽略。
- 前端多了一份 `localStorage` 提交检查点（`jiese-pending-v1:<昵称>`），提交成功的路径上会被清掉。

### 诚实说明：这不是严格互斥，也不可能做到

- **KV 没有 CAS**，「读状态 → 干活 → 写状态」不是原子的。`inflight` 只是一层**软锁**：
  它挡的是「同一次提交的两份请求撞在一起」，不是并发上限。跨 colo 不保证——不过浏览器到
  Pages Function 基本落在同一个 colo，而 ADR-0007 已实测「写入发生的 colo 会同步失效该键读缓存」，
  对同一个用户的两次并发够用。
- **两次非事务存储之间不存在真正的 at-most-once**。本方案把「用户可自由重试」那段大窗口，
  缩小到「钉 done 与上一次写之间的一次 KV 调用」。剩下的极端崩溃窗口仍然存在，如实记在这里。
- **ima 落库中途失败（部分写入）无法回滚**。此时会把状态放回 `prepared` 让用户能立刻重交
  （不把「失败」谎报成「进行中」干等 60 秒），重交可能重复那些已经写进去的条目——
  与不使用幂等键时的风险相同，本 ADR 不新增也不消除它。
- **判不了「今天是否已打卡」时一律放行**（`get` 抛错 → 视为无记录），并写 `[finalize]` 告警。
  降级方向沿用 ADR-0004 / 0008：宁可偶发重复登记，也不能因 KV 故障让成员打不上卡。
- **`submission_id` 不防伪**：知道格式的人可以自己编一个——但编出来的 id 从未被签发过，
  只会撞上 `submission_unknown` 被拒。重放攻击不在本项目的威胁模型里（ADR-0002 的取舍）。

## 备选方案（未采纳）

- **(b) 按「昵称 + 日期」天然幂等**：服务端更简单，但必须放弃「同一天可多次打卡」，
  且不能区分「重试」与「再打一次」。超出本票授权，需回到地图层面确认。
- **复用 `image.media_id` 当幂等键**：零契约新增字段，但把幂等键绑死在 ima 的 `media_id` 命名上，
  也失去了「在 prepare 阶段就绑定昵称+日期」这层校验。
- **`prepare` 改发 HMAC 票据（把幂等键一起签进去）**：ADR-0005 记的加固路径。
  本期不必要（持邀请码者本就可任意打卡），但契约形状已为它留好。

## 验证

`.workbuddy/tests/idempotency.test.mjs`（41 项）直调真实 `prepare` / `finalize`，桩化 KV 与 ima 出站 HTTP
（`ima-fake.mjs` 已补 `create_media`、`add_knowledge` 失败开关与 KV 写入选项记录），覆盖：

- 同一 `submission_id` 重复 finalize → 第二次 `status: already`，**零 ima 请求、零 KV 写**；
- 未签发 / 昵称不匹配 / 跨天的 `submission_id` → 409 且不落库；
- 自然日闸门未确认 → 409 `duplicate_day` 且不写；确认后放行且**仍落在同一个日期文件夹**
  （「一天多次」未被误伤）；
- inflight 生效中 → 409；窗口过期后放行（僵死不会永久卡住成员）；
- 统计写失败 → `stats_updated:false`；重交补写统计但**不再碰 ima**；
- 判不了本日状态 → 放行且留痕；幂等记录读失败 → 503 可重试且不落库。

`.workbuddy/tests/checkin-flow.test.mjs`（37 项）用 jsdom 驱动真实 `index.html` + `app.js`，覆盖
「结果未知 → 重交不再调 prepare、不再重传、复用同一 id」「今天已打过卡 → 就地确认后带
`allow_duplicate_day` 重发」「刷新页面后仍能重交」「跨天检查点作废」。

`.workbuddy/tests/endpoints.test.mjs`（45 项）同步更新后全绿——ADR-0008 的目录与降级行为未被破坏。
`tests/ima-auth.test.mjs` 的 env 补上了 KV 绑定（`prepare` 现在会先落幂等记录）。

验收问题：「用户在网络抖动后，按原型给的按钮点下去，会不会产生第二次登记？」
答：**不会**，且响应能区分 `new` 与 `already`。
